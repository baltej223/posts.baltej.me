# Why concurrency is not always preferable.

On 26 May, 2026, I was working on one of my projects, which was writing a [**HTTP Sever from Scratch in C**](https://github.com/baltej223/HTTP_in_C), where I wrote **HTTP Parser and HTTP response generator**. I was trying to make the system/server concurrent for better performance.

I was using the standard socket library provided by C.

```C
#include <sys/socket.h>
int socket(int domain, int type, int protocol);
```

One of the most important engineering decision that I took while  building it was that, I was sequentially reading the **HTTP stream** and then was processing it.

### **Which means if two requests come at almost same time?**

Even if they arrive at **exactly** the same time, there isn't really a meaningful concept of "the exact same instant" at the software level. The network stack will eventually present the data to the server in some order.
Cause of which only one request can be processed at an instant, and other requests wait in the queue.
Just like a **FIFO Queue** with a fixed length.

### If more requests arrive than the OS is configured to handle, OS just drops those requests.

The HTTP response was very simple, just a few headers and response body.

Exact HTTP Response to a standard curl get request:

```HTTP
User-Agent: curl/8.15.0
Accept: */*

HTTP/1.1 200 OK
Server: C-Server
Date: Fri Mar 27 18:52:02 2026
Content-Length: 47
Content-Type: text/plain

This is the data to be sent back to the client!
```

Notice that it don't require any logic to generate response body, its just standard `This is the data to be sent back to the client!`.

Initially I made the server synchronous, but on `26 May, 2026` I used `pthreads.h in C` and converted the server to use threading.

### Surprisingly when I benchmarked the server, its performance degraded! Single thread, non epoll version of server was preforming better

In this case, the server was pretty computationally small and thread creation overhead was too much!

Therefore, the mental model that concurrency speeds things up is incorrect; it should only be utilized when it is appropriate. In fact, concurrency is not always faster or better.
